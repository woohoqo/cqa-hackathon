## Уровни проверки

1. QA unit: аудитор, группировка, независимый расчёт, метрики и происхождение меток. Синтетические тесты этих утилит не подтверждают работоспособность приложения.
2. Backend integration: настоящие модели, расчёт, FastAPI/SQLite, очередь и апелляции с явно внедрённым test-only evaluator. Это проверяет приложение, но не API модели.
3. Provider mock: настоящий AI-модуль с перехватом запроса к провайдеру, изменением текста/ID критерия, кэша и внедрённой инструкцией. Пока AI заглушка — блокировано.
4. Live API: настоящий провайдер, исходный ответ и все попытки. Отдельные синтетические проверки prompt injection. Пока не выполнено.
5. UI end-to-end: импорт → версия чек-листа → обработка → доказательство → апелляция → решение → повторное открытие → изменение критерия. Пока frontend пуст — блокировано.

`qa/test_product_contract.py` задаёт 12 приёмочных наблюдений. Без `CQA_QA_ADAPTER` они честно пропускаются с BLOCKED, а не считаются успешными. Будущий QA-owned модуль `probe(case, fixture)` должен вызывать настоящий код и возвращать наблюдения, которые утверждаются в тестах. Нельзя реализовать probe возвратом заранее ожидаемых значений. Независимые backend-тесты выполняются отдельно и могут покрывать часть тех же требований. Для №8/12 прохождение backend-передачи объекта не доказывает содержание запроса провайдеру или устойчивость модели.

## Предложения интегратору (не изменения контракта)

- Для честной стоимости/времени нужны данные каждой попытки провайдера: evaluation_id, attempt number, provider/model/prompt version, start/end, latency, token usage, стоимость/валюта/источник цены, cache hit и error category. Сейчас EvaluationDraft содержит provider/model/prompt_version и raw_response, но не usage/attempt ledger. Неизвестное значение сохранять null.
- Экспорт должен сохранять неудачные оценки. При внутренних retry одной успешной Evaluation недостаточно для учёта всех API-ошибок и расходов; нужен отдельный журнал попыток или согласованный QA sidecar.
- Для сравнения нужны внешний ID разговора и хеш фактически оценённого текста плюс полный хеш конфигурации. Conversation и checklist_snapshot позволяют построить это в QA-адаптере, не добавляя поля общему API.
- В pytest.ini сейчас testpaths только backend/tests. Для интеграционного gate запускать явно `python -m pytest backend/tests qa -q`; изменение общего CI/конфига выполняет агент 1.

AI-владельцу: после публикации проверить фактический исходящий запрос при изменении смысла критерия и новом ID; источник правил — snapshot. Внедрение внутри транскрипта остаётся данными. Кэш зависит от всего текста/ролей/порядка/времени и конфигурации, модели и prompt version. Ответы holdout в промпты не передавать.

UI-владельцу: доказательство прокручивает к существующему message ID; N/A и null total различаются; failed показывает ошибку без успешного балла; raw AI/original/final представлены раздельно; при новой версии повторная оценка действительно запускается.

## Формат дефекта

ID / severity / владелец / проверенный commit / mock или live; шаги; минимальный синтетический вход (или приватный ID/хеш без текста); ожидаемое с основанием (страница Checklist/Guide или контракт); фактическое; доказательство; статус исправления и повторной проверки. Возможный риск без воспроизведения на приложении обозначать как гипотезу, не как найденный bug.
