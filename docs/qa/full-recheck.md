## AI-QA-003: модель отрицает явно присутствующее извинение

- Приоритет: P1 для задания изменения критерия/точности; ответственный участник2, участник1 контролирует интеграцию.
- Вход: второй разговор того же fixture, external_id=qa-final-apology-change. Конфигурация `qa/fixtures/live-apology-checklist.json` — тело для POST /api/v1/checklists; это синтетическая тестовая конфигурация, не замена shared contract.
- Шаги: сохранить конфигурацию (№1 требует явного извинения, плюс девятый zero-weight критерий), импортировать второй разговор, оценить его новой версией.
- В сообщении qa-m3 реально сохранено: «Прошу прощения за ожидание. Здравствуйте! Меня зовут Анна…». Содержимое повторно прочитано через API и видно в браузере.
- Ожидается №1=true по новому буквальному правилу. При остальных наблюдённых ответах ожидается100,00.
- Фактически №1=false, итог84,62. Пояснение: «Оператор поздоровался и представился, но явно не извинялся перед клиентом». Evidence ссылается на то же qa-m3, содержащее извинение. Таким образом, существование evidence ID не гарантирует правильность вывода.
- Предложение AI-владельцу: воспроизвести оба синтетических случая, проверить приоритет текущего описания над прежним названием и проверку соответствия rationale/evidence. Не вводить исправление только для фиксированного ID/фразы, не выдавать дополнительные LLM-ответы за ground truth. Сначала измерить изменения на согласованной tuning-разметке; holdout не передавался.

## Решение QA

Можно демонстрировать работающий интерфейс, расчёт и review workflow. Нельзя заявлять «все требования полностью подтверждены» или «AI точен на100%». До финальной защиты приоритетны AI-QA-002/003, согласованная человеческая разметка, рабочий путь прослушивания/внешнего плеера и решение публикации репозитория. Production исправляет соответствующий владелец; этот QA-этап публикует доказательства и воспроизводимые синтетические входы.
