## D365-QA-001: текущая сборка зависит от корня сайта

Ответственный: участник 3 (frontend). Статус: подтверждённая необходимость адаптации для прямого размещения как HTML web resources; не дефект текущего standalone-запуска.

1. Собрать frontend стандартной командой `pnpm --dir frontend build` (сборка выполнена при запуске приложения).
2. Прочитать dist/index.html: ссылки на скрипт/стиль начинаются с `/assets/`.
3. Разрешить эти ссылки относительно условного `https://example.invalid/WebResources/new_cqa/index.html` через стандартный urllib.parse.urljoin.
4. Фактически получаются `https://example.invalid/assets/...`, а не пути внутри `/WebResources/new_cqa/`. В src/fonts.css также есть `/fonts/...`, а в App.tsx/DialogueList.tsx — `/media/...`.

Ожидаемое для пакета web resources: все ссылки приводят к ресурсам, опубликованным под согласованным префиксом. Основание — инструкция Microsoft выше. Простого копирования dist недостаточно. Предложение: отдельный профиль сборки с нужным base/относительными ссылками, обработка public media/font paths, проверка поддерживаемых типов ресурсов и упаковка с publisher prefix. Одного изменения Vite base может быть недостаточно для строк `/media/...` в компонентах.

## D365-QA-002: адрес API и CORS нужны для отдельно размещённого UI

Ответственные: участник 1 (развёртывание/CORS), участник 3 (профиль сборки). Статус: подтверждённая настройка, необходимая при прямом размещении frontend на Dynamics-origin.

При пустом VITE_API_BASE_URL запрос `/api/v1/...` адресуется origin текущей страницы. В Dynamics это был бы сервер Dynamics, а не наш FastAPI. Кроме того, OPTIONS к локальному `/api/v1/checklists` с тестовым Origin `https://example.crm4.dynamics.com` и Access-Control-Request-Method=GET вернул **400**, Access-Control-Allow-Origin отсутствует. Реальный tenant не вызывался. Это ожидаемое поведение текущего локального allowlist, не причина открыть CORS всем сайтам.

Для этого способа размещения нужен HTTPS API, VITE_API_BASE_URL с его адресом и точный разрешённый origin организации. Backend сейчас разрешает Content-Type; будущая схема Authorization потребует отдельного согласованного изменения. Учёт доступа и подключение Dataverse не реализованы и не требуются для локального демо без регистрации.

## Два возможных пути дальнейшей адаптации

1. Отдельно размещённое приложение внутри iframe Dynamics. При frontend и API на одном внешнем origin пути `/assets` и `/api` остаются рабочими: описанные выше проблемы прямого копирования на Dynamics-origin сюда автоматически не переносятся. Нужны HTTPS hosting, проверка iframe policies, допустимой схемы входа и фактический прогон в tenant.
2. HTML/JS/CSS как Dynamics web resources плюс отдельный API. Нужны перечисленные изменения путей/упаковки и API/CORS. Если требуется открывать диалог из CRM-карточки, добавить адаптер record context; сейчас query parameters Dynamics не обрабатываются.

Microsoft описывает iframe внешних страниц, frame-ancestors/X-Frame-Options и проверяемый postMessage для обмена с другой origin; для интерактивных компонентов рекомендует рассмотреть PCF. Это выбор будущей интеграции, не дополнительное требование хакатона: [IFRAME and web resource controls](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/use-iframe-and-web-resource-controls-on-a-form).

В локальном GET / заголовки X-Frame-Options и CSP отсутствуют. Это отсутствие явного серверного запрета в проверенном ответе, **не успешный iframe-тест**. Настройки будущего hosting/proxy и формы Dynamics могут отличаться. Внешний iframe не получает прямой доступ к DOM/Xrm родителя; при необходимости нужен явный адаптер контекста.

Microsoft также предупреждает, что HTML control может уничтожаться/инициализироваться при переходе между вкладками. Наши сохранённые оценки находятся на сервере; несохранённый React state редактора не переживает такой remount. Для интеграции нужно определить поведение черновиков и проверить повторную инициализацию.
